# ADR 0005 — Generated learner support is a build artifact, not a runtime service

- **Status:** Accepted
- **Date:** 2026-09-04
- **Upholds:** [ADR 0002](0002-fetch-the-catalogue-at-build-time.md), which named the
  condition under which it should be revisited. This ADR checks that condition against a
  concrete feature, finds it unmet, and records why — so the next feature that asks the
  same question starts from an answer rather than from the question.
- **Unblocks:** [R24](../REQUIREMENTS.md#r24--in-other-words-elaborated-restatement-in-the-target-language)

## Context

[R24](../REQUIREMENTS.md) adds a middle rung to reading support: a learner taps a cue and
gets the same sentence said differently, still in the target language, with the difficult
expression kept and explained in place. The text is generated by a model.

The requirement declares itself blocked on ADR 0002 and offers two routes: revisit ADR
0002 and give the app a runtime API for generation, caching and telemetry, or generate at
build time into the catalogue. It states that the first is "the route the requirement as
written assumes."

That reading is worth taking seriously, because ADR 0002 does not claim to be permanent.
It names its own expiry:

> A catalogue change requires a web rebuild. Correct for a seeded catalogue on a
> commit-driven deploy; it will not survive user-specific ranking or a real ingestion
> pipeline. **When the catalogue becomes per-learner or updates between deploys, this
> decision gets revisited.**

So the question this ADR answers is narrow and answerable: **does R24 make the catalogue
per-learner, or make it update between deploys?**

It does neither. And the requirement says so itself, in the two criteria that describe
where the generated text lives.

## Decision

### 1. Rung-2 restatements are generated at build time, into the catalogue

R24's own cache specification decides this, in two lines:

> 10. Keyed by episode id + cue index + level. **Not per learner** — two learners at the
>     same level on the same cue get the same text and the second is free.
>
> 11. Cached restatements survive a restart, **in the same store as the transcript**.

Criterion 10 says the key contains no learner. Content keyed on (episode, cue, level)
changes only when one of those three changes, and all three come from
`catalog.seed.json` — so it changes on a commit, which is exactly the deploy cadence ADR
0002 was written for. Criterion 11 then says to put it where the transcript is. In this
repo the transcript is a field in the seed. Followed literally, criterion 11 lands on
build time; it reads as a runtime requirement only against a system that has a runtime
transcript cache, and this one does not.

A restatement is not a response to a learner. It is a second rendering of a line the
catalogue already ships, deterministic in the same inputs. That makes it catalogue
content, and catalogue content is built.

### 2. ADR 0002 is not revisited, and its condition is not weakened to fit

The temptation here is to read "the browser never calls the API" as a constraint to be
routed around. It is not a constraint; it is a consequence of the catalogue being
static, and the catalogue is still static.

Three costs stand behind that, in descending order of how much they should have mattered:

**The API has no persistence of any kind.** `apps/api/src` is four modules — `catalog`,
`health`, `ingest`, `vocabulary` — and every one of them holds its data in memory. There
is no database, no ORM, no cache server, no file write. Criterion 11 says cached
restatements must survive a restart; on the runtime route, satisfying it means
introducing a datastore that nothing else in the product needs, for content that does not
change between deploys. Build time satisfies criterion 11 for free, because a file
survives a restart by being a file.

**Cold start is worse here than the case ADR 0002 already rejected.** `discopod-api` is on
a free plan that sleeps after fifteen idle minutes and takes tens of seconds to wake. ADR
0002 weighed that against a page load. A tap-to-reveal is more sensitive to latency, not
less: a learner stopped mid-sentence, who has already admitted they cannot follow the
line, is the worst possible person to make wait. The failure mode of a slow rung 2 is not
a slow feature — it is a learner who stops tapping.

**Nothing dynamic is exchanged.** Runtime generation would ask the model the same question
for every learner at a level and get the same answer, then pay for it each time.

### 3. Proactive generation is the trade, and R24's stated reason against it does not hold

R24 lists proactive rewriting as out of scope, on the grounds that on-demand generation is
"what makes the rung-of-resolution signal meaningful." R24's own "Blocked on" section
already retracts this, and it is right to: the signal is which rung the learner
**opened**, and that is observed at the tap regardless of when the text behind it was
produced. Pre-generating rung 2 does not tell us a learner used it.

So the exclusion is traded away, and what is actually paid for is money and build time.
State the size honestly. The seed lesson is 30 seconds with 8 cues — roughly 16 cues per
minute. A 30-minute episode is therefore around 480 cues, times three levels, about 1,440
generations. That is a one-off cost per episode, amortised over every learner who ever
opens it, against a per-learner-per-tap cost forever on the other route. Today's entire
catalogue is one lesson: 8 cues × 3 levels = 24 generations.

At a hundred episodes this is ~144,000 generations and the arithmetic deserves revisiting
— but the mitigation then is to generate only for cues above a difficulty threshold, which
is a tuning parameter, not a change of architecture. That is a materially different
decision from the one this ADR makes, and it is not made here.

Build time also buys something the runtime route cannot: **the corpus is reviewable before
it ships.** Given the risk R24 identifies — a bad restatement is invisible, because not
understanding the original is the reason the learner asked — being able to read the
generated text before a learner does is worth more than it costs. Criterion 9's
"retry once, then hide rung 2" works unchanged at build time: the cue simply ships without
a rung 2.

### 4. Copyright is a source-licensing question, not a generation-timing one

R24 raises the concern that stored derivatives sit differently from transient analysis.
The distinction is real in general and does not apply here, because it does not separate
the restatement from the transcript.

The transcript is already generated, already stored in the seed, and already shipped as
static HTML to every visitor. A restatement is a derivative of a text we are, by that
point, distributing. If distributing the transcript is defensible, so is distributing a
derived rendering of it; if it is not, the app has a problem that predates this feature
and generating on demand does not fix it.

The lever that controls this is the audio source's licence, which is where the FSI /
public-domain question lives. Generation timing is not a copyright control and must not be
chosen as if it were.

That question is now answered by
[ADR 0007](0007-fsi-is-a-pipeline-fixture-not-a-catalogue-source.md), and the answer is
that a clean licence was necessary and not sufficient: FSI's tapes are freely
distributable and still unfit to ship, so the first Mandarin content has to be licensed
from a publisher rather than found in the public domain.

### 5. Telemetry is deferred together with its consumer

Criteria 12 and 13 are the one part of R24 that genuinely needs a runtime: the browser
emitting `rungReached` somewhere. They are deferred, and not because they are hard.

They are a specification for how a level estimator should weigh rung-2 events against
rung-3 events. **No level estimator exists.** `DifficultyProfile.level` is a property of
the episode, picked by the learner from three buttons; nothing in the codebase models a
learner's level at all. There is also no telemetry path of any kind — saved words live in
`localStorage` and nothing is sent anywhere, so emitting per-cue events is a new
capability carrying its own privacy decision.

Building an outbound path for a consumer that does not exist would fix the shape of the
data before anything reads it, which is the reliable way to get that shape wrong. Rungs
1–3 ship without measurement; criteria 12–13 land with the estimator, and the runtime
question gets asked then, on that feature's evidence rather than this one's.

## What this ADR does not do

- **It does not build R24.** No prompt is wired, no generation script exists, no field is
  added to the catalogue schema. This decides the shape; the feature is still unstarted.
- **It does not choose a model or a provider.** There is no LLM dependency anywhere in the
  repo today. Adding one is a decision with its own cost and failure modes, made when the
  generation step is written.
- **It does not settle Chinese elaboration.** R24 is explicit that the prompt does not
  transfer — segmentation, 白話 register-shifting, script variant. Shipping English first
  is the requirement's own instruction and nothing here changes it.
- **It does not fix `LanguageTag` or `proficiency`.** The prompt takes a level band, and
  [ADR 0003](0003-model-the-learner-language-pair.md) decision 7 remains outstanding with
  a third caller now waiting on it.
- **It does not close the runtime question forever.** It answers it for R24.

## Consequences we accept

- **Every restatement is paid for, most are never read.** A learner taps a handful of
  cues in an episode; the build generates all of them at all three levels. This is the
  real cost of the decision and it is accepted knowingly, because the alternative charges
  per learner per tap with no ceiling and no reuse.
- **Rung 2 for a new episode arrives on a deploy, not on ingestion.** Same property the
  catalogue already has, extended to a second kind of content. An ingestion pipeline that
  adds episodes between deploys breaks this — and it also breaks ADR 0002, which is the
  point: the two now fail together, at the same seam, rather than one of them quietly
  degrading.
- **Bad generated text ships to everyone, or to no one.** There is no per-learner
  regeneration and no feedback loop. Criteria 6–9's validation runs at build time and its
  failures are build-time failures. In exchange, a bad restatement is catchable by a human
  reading the corpus, which the on-demand route makes impossible by construction.
- **The generation step joins the build's critical path.** `build.mjs` already spawns the
  API and health-checks it before `next build`; a generation step is a third thing that
  can fail a deploy. It must be cacheable on the seed's content, or a one-word edit to a
  transcript re-generates a catalogue.
- **`STATIC_EXPORT=1` remains the only thing standing between here and a runtime.**
  `next.config.ts:14` gates `output: 'export'` on that variable, and `discopod-api` is
  already deployed with a health check. If the level estimator or a real ingestion
  pipeline forces the question, the reversal is an environment variable and a
  `catalogue.ts` change — the seam ADR 0002 named. This decision is cheap to unmake, which
  is part of why it is safe to make now.
